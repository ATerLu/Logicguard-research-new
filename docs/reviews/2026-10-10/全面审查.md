## 严重问题

### P1-1：无效攻击响应会被记为 `generation_valid=true`

证据：

- [execution_protocols.py:77](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/src/logicguard/benchmark/execution_protocols.py#L77) 对 A1 使用 `str(...)`，因此 JSON `null` 会变成字符串 `"None"`。
- [execution_protocols.py:209](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/src/logicguard/benchmark/execution_protocols.py#L209) 的 A3 只检查字段名存在，不检查字段类型、非空内容或列表元素。
- [attack_runner.py:205](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/src/logicguard/benchmark/attack_runner.py#L205) 三阶段通过后无条件写入 `generation_valid=true`。

离线复现：

```text
A1 {"target_answer":null,"malicious_texts":[null]}
=> {'target_answer': 'None', 'malicious_texts': ['None']}

A3 三阶段字段全部为 null/空列表
=> generation_valid=True, phases_completed=3,
   provider_calls_made=3, error=None
```

影响：虚增生成有效率，固定分母中的有效生成数失真；A3 会在第一阶段输出无效时继续消耗后续请求，之后才可能在物化环节失败。

建议：为每个阶段使用严格 schema（字段类型、字符串非空、列表元素和数量）；阶段校验失败立即标记 invalid，并禁止依赖它的后续槽 dispatch。补充 null、空列表、错误元素类型和跨阶段依赖测试。

### P1-2：旧付费 runner 中断后可重复同一付费请求

证据：

- [attack_runner.py:275](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/src/logicguard/benchmark/attack_runner.py#L275) 只根据结果/summary 文件是否存在拒绝重跑。
- [attack_runner.py:319](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/src/logicguard/benchmark/attack_runner.py#L319) 把所有 attempt 收集到内存，全部完成后才写结果。
- 新的 `RequestCostGuard` 虽实现了 in-flight fail-closed，但 manifest 仍声明它尚未绑定到这个旧 runner；不能把新 guard 当成已经保护了 paid path。

离线复现：第一次 provider 调用抛出 `KeyboardInterrupt`，结果/summary 尚未落盘；第二次运行通过文件检查并再次发起同一攻击请求，fake client 的调用计数从 1 变成 2。这证明存在重复发起请求与重复扣费风险，不代表本次产生了真实扣费。

同一路径还存在两个相关风险：

- [attack_runner.py:169](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/src/logicguard/benchmark/attack_runner.py#L169) 把缺失 usage 当作 0；合法文本但 usage 全为 `None` 时仍会得到 `generation_valid=true`、零成本。
- 成本仅在全部调用结束后汇总（[attack_runner.py:330](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/src/logicguard/benchmark/attack_runner.py#L330)），单次未知 usage 或越界无法阻止后续调用。

建议：付费 runner 必须在每次调用前使用统一 guard 持久化 slot，在调用后原子写入结果与 usage；中断留下 `in_flight/unknown` 时禁止继续 dispatch；未知 usage 不能折算为零；把预算检查从批末移到每个 request 的 reserve/reconcile 边界。

### P1-3：普通测试会覆盖冻结历史实验产物

证据：

- [tests/test_comparative_benchmark_e0.py:21](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/tests/test_comparative_benchmark_e0.py#L21) 直接指向仓库内 `artifacts/benchmark/e0`。
- [tests/test_comparative_benchmark_e0.py:141](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/tests/test_comparative_benchmark_e0.py#L141) 调用真实配置并重复写入。
- [readiness.py:823](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/src/logicguard/benchmark/readiness.py#L823) 在后续数据完整性检查之前就写 asset manifest。

实际发生过：缺少数据导致测试失败，但已经把提交中的历史 manifest 改成了 `missing`。本次已恢复；问题本身仍存在。

建议：测试全部使用 `tmp_path` 或临时 namespace；冻结资产测试改为只读 hash/内容校验；集成构建与单元测试分离，缺外部资产时显式 skip 或给出独立 fixture。

## P2 工程与实验完整性问题

### P2-1：截断 checkpoint 恢复后追加会破坏 JSONL

[core/io.py:16](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/src/logicguard/core/io.py#L16) 在 `tolerate_trailing_partial=True` 时忽略不完整尾行，但不截断文件；[append_jsonl 64](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/src/logicguard/core/io.py#L64) 直接追加。复现结果：

```text
{"run_fingerprint":"fp"{"run_fingerprint":"fp","case":"resumed"}
=> 下次 load_jsonl 抛 JSONDecodeError
```

回答生成在 [answer_generation.py:457](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/src/logicguard/evaluation/answer_generation.py#L457) 采用“读取 checkpoint 后追加”模式。建议提供显式恢复步骤：先隔离保留残缺尾部，再原子重写有效行或修复尾部后追加；补充“截断、恢复、追加、再次读取”的测试。

### P2-2：成本守卫对已知超支的实际费用低报

[request_cost_guard.py:157](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/src/logicguard/benchmark/request_cost_guard.py#L157) 在超支时已保存 `actual_cost_cny` 并将状态置为 `cost_violation`，但 [summary 257](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/src/logicguard/benchmark/request_cost_guard.py#L257) 只统计 `complete/invalid_schema`，[_committed_cost 314](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/src/logicguard/benchmark/request_cost_guard.py#L314) 对 `cost_violation` 使用 reservation。复现：实际 ¥0.0002、预留 ¥0.0001，摘要却报告 known=0、reserved_or_charged=¥0.0001。停止调度仍有效，但审计金额不准确。建议已知实际 usage 的异常请求至少按 `actual_cost_cny` 计入，并明确 `max(actual,reserved)` 规则。

### P2-3：公平信息审计只信任自报 hash

[trusted_controls.py:227](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/src/logicguard/benchmark/trusted_controls.py#L227) 只比较行内的 hash 字符串，不重算 candidate pool、budget 或实际来源。复制合法 T1 行为 D6，替换 `selected_sources`、把 `max_context_tokens` 改为 999，同时保留 hash，审计仍返回 `passed=true`；两个空对象也会通过。建议 schema 必填、从实际内容重新计算 hash，并校验真实来源和使用量。

### P2-4：可信快照忽略冻结正文 hash

`build_trust_manifest` 在 [trust_manifest.py:123](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/src/logicguard/benchmark/trust_manifest.py#L123) 保存 `clean_group_sha256`，但 [materialize_protected_snapshot:167](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/src/logicguard/benchmark/trust_manifest.py#L167) 只检查 source group 集合。相同文档 ID/组 ID、正文从 `Original` 改为 `Poisoned` 时仍可物化。当前 fixture runner 是同一份 clean 文档即时生成 manifest 和 snapshot，暂无证据表明冻结资产已污染；这是恢复/跨进程物化必须补的完整性门。

### P2-5：T1 同组 RRF 可能保留最差 trusted chunk

[trusted_controls.py:138](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/src/logicguard/benchmark/trusted_controls.py#L138) 对同一 source group 无条件用最后一个 trusted hit 覆盖 `entry["hit"]`，但 `best_rank` 仍保留最小 rank。rank=1 的好证据、rank=2 的无关证据会输出后者并报告 `best_rank=1`，可能削弱 T1 基线并影响 D6 公平对照。建议保留同组最佳 chunk，或明确文档/chunk 级融合规则。

## 研究就绪度与不能过度宣称的边界

以下不是本次新增代码缺陷，而是当前项目状态必须写进实验结论的限制。依据：[handoff.md](../../../handoff.md)、[v1.2 预注册](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/docs/comparativeExperimentPreregistration_v1.2.md#L31)、[当前协议](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/configs/benchmark/comparison_v1_2_protocol.yaml#L30) 和 [dev60 冻结边界](https://github.com/ATerLu/Logicguard-research-new/blob/1bad5928753a786261d98637094115334eba3fbf/docs/Dev60_LaunchGuard_WP2_Freeze.md#L69)。


- Stage48 Gate A 已失败并关闭；WP1 完成、WP2 仅部分完成，完整 dev60 尚未付费执行。
- 三个数据集各 500 问都有历史执行记录，覆盖原 development/validation/locked-test；这不等于证明所有 gold 被看过或已经发生数据泄漏，但目前不能认证它们是未触达的新确认集，不能仅改名就将同一批数据当作 fresh holdout。
- 真实 trusted-pool retrieval、D6 四组件、D4 bounded implementation 仍未完成；D4 官方工件因编译错误和缺 prompt unavailable。
- A3 的关系攻击终点、单位和问题相关性仍需在正式效果评测前冻结。
- D3 固定工件虽有 anchor，但存在 MiniLM 顺序敏感和论文公式差异；不能据此推出一般性防御效果。
- provider alias 没有不可变 revision，`attack_seed` 只是记录元数据，并未作为 provider RNG seed 传入；可复现性应表述为“冻结请求/共享生成资产”，不是权重级完全复现。
- 预注册 v1.2 对 A2 的旧 query-stage 描述与新四阶段本地 pipeline 并存，应标清历史 runner 与当前 WP2 pipeline，避免读者误解状态。

因此目前不能宣称 LogicGuard 已优于外部防御、已获得统计显著优势、已完成三数据集正式比较，或已抵御针对最终 D6 的自适应攻击。

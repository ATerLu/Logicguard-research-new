## 2. 项目目标

LogicGuard 研究 RAG / GraphRAG 在逻辑污染或语料污染攻击下的防御问题。核心目标是：

- 识别被污染或高风险证据；
- 阻断污染证据进入最终上下文；
- 用可信证据 recovery，避免系统只会拒答；
- 在回答层验证最终回答是否被污染影响。

项目当前围绕 LogicPoison / GraphRAG poisoning 方向展开，重点关注多跳问答数据集中的 evidence poisoning、实体关系误导和 GraphRAG 查询层上下文污染。

## 4. 当前 LogicGuard 三阶段流程

### 阶段一：风险识别

目标：判断检索到的证据是否可能受到逻辑投毒影响。

当前用到的风险信号：
- 文档是否属于 changed / poisoned support；
- 实体是否异常、泛化或与问题实体冲突；
- 证据来源是否与干净证据或可信证据不一致；
- official GraphRAG `context_data.sources` 是否包含 changed support doc_id。

### 阶段二：Guard 过滤或抑制

目标：减少可疑证据进入最终上下文。

当前实现：
- 在 BM25 / graph surrogate 中直接过滤 changed support 或异常证据；
- 在 Microsoft GraphRAG official query 层中用 include / exclude entities、query rewrite、source budget 影响 `LocalSearchMixedContext`；
- 在 official sources 后处理层中生成 `guarded_sources`，删除 changed source。

### 阶段三：Recovery 恢复

目标：移除污染证据后，用可信证据补回上下文，避免系统只会拒答。

当前层级：
- Oracle recovery：使用 clean reference 或 doc_id 对齐，作为上界实验。
- Non-oracle recovery：不直接使用答案标签或 doc_id lookup，而是根据 query、title、entity、text similarity 等恢复证据。
- Official GraphRAG sources recovery：直接读取 official GraphRAG 的 `context_data.sources`，识别 changed source，再用可信候选替换。

## 6. 可靠结论

1. LogicPoison 类污染可以显著提高污染证据暴露，攻击不是空想。
2. 单纯 guard 能降低污染暴露，但会造成上下文为空、回答 unknown 或召回崩溃。
3. Recovery 是 LogicGuard 能保持可用性的核心模块。
4. Microsoft GraphRAG official query layer 已经可以接入并生成实验上下文。
5. Stage23/24 在 official `context_data.sources` 层证明 oracle recovery 上界成立。
6. Stage25 初步证明：非 oracle candidate recovery 也能明显恢复 recall，并保持 changed exposure 为 0。
7. Stage26 初步证明：最佳 non-oracle recovery 在 answer proxy 上也优于只删除 source。
8. Stage27 初步证明：recovery 能把真实回答层 attack-success 降到 0，但当前 utility 仍不足。
9. Stage28 初步证明：risk oracle 可以被 clean-candidate consistency detector 替换，并保持 attack-success 抑制。

## 8. 当前主要研究缺口

### 缺口一：clean corpus / trusted candidate 假设仍强

Stage25 已经不按 doc_id 直接取 clean source，但候选池仍来自 trusted clean/reference artifacts。

后续需要：
- no-clean setting；
- trust-aware retrieval；
- uncertainty-aware recovery；
- 多源交叉验证；
- 只使用局部可信候选而非全局 clean corpus。

### 缺口二：风险触发仍是 oracle

Stage25 属于 `risk_oracle + recovery_non_oracle`。下一步需要设计 `risk_non_oracle + recovery_non_oracle`。

可选方向：
- changed source classifier；
- source consistency detector；
- entity contradiction / bridge inconsistency detector；
- uncertainty threshold；
- 多证据一致性投票。

### 缺口三：缺少 answer-level 验证

当前 Stage23/24/25 主要是 context-only 指标。必须补充 LLM answer-level 验证，评价：
- correct；
- partial；
- wrong；
- abstained / unknown；
- attack success；
- evidence faithfulness。

### 缺口四：缺少自适应攻击

自适应攻击应在防御参数冻结后进行。

建议攻击层级：
- A0：非自适应攻击，攻击者不知道防御。
- A1：黑盒自适应，攻击者知道有防御但不知道规则。
- A2：灰盒自适应，攻击者知道主要风险特征。
- A3：白盒自适应，攻击者知道过滤和 recovery 逻辑。

注意：自适应攻击必须作为本地科研验证，不连接真实生产系统，不做未授权测试。

### 缺口五：现代 RAG baseline 不够完整

当前已有 BM25、轻量图代理、Microsoft GraphRAG official query layer，但还需要：
- BM25；
- dense embedding retrieval；
- hybrid retrieval；
- reranker；
- NaiveRAG；
- GraphRAG / Microsoft GraphRAG local query；
- 可能的 GFM-RAG / HippoRAG2 对照。

## 9. 下一阶段最高优先级任务

推荐下一阶段命名为：

```text
Stage29：Adaptive Attack Evaluation
```

目标：
在 Stage28 已去掉 risk oracle 的基础上，设计自适应攻击，专门攻击 clean-candidate consistency detector、title/entity BM25 recovery 和 trusted clean candidate pool 假设。

输入：
- Stage28 source-level contexts、risk features 和 recovered contexts；
- Stage28 answer proxy / real LLM outputs；
- clean/reference candidate pool；
- 攻击候选生成器，不得读取 gold answer 作为生成特征；
- query / answer / support metadata 仅用于离线评价。

建议处理流程：
1. 定义 A1/A2/A3 自适应攻击：低实体漂移改写、标题保持/正文微扰、candidate pool collision。
2. 在 5-query 上做 attack smoke，确认攻击能绕过 detector 或降低 recovery 排序。
3. 扩展到 20-query，对比 Stage28 原始攻击与 adaptive attack 后的 risk recall、changed exposure、answer proxy 和 real LLM。
4. 报告 attack budget、detector evasion、bad replacement、answer attack-success。
5. 冻结 adaptive attack protocol，为论文鲁棒性实验做准备。

验收标准：
- 攻击生成不直接使用 gold answer 作为生成特征。
- 同时报告 detector evasion、source-level changed exposure、answer proxy 和 real LLM attack-success。
- 能说明 Stage28 的 clean-candidate consistency detector 是否被 adaptive attack 绕过。
- 不能把 Stage28 的当前 0 attack-success 当成自适应攻击下的最终结论。

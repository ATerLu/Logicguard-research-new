# LogicGuard 论文实验矩阵（2026-06-20 冻结版）

## 1. 冻结规则

本矩阵只整理已经生成并可由文件证据核验的结果，不补算、不修改历史指标，也不把诊断实验包装成防御成功。每项实验使用 `LG-*` 唯一编号；完整配置、输入、输出、报告和哈希见 `docs/实验注册表.csv` 与 `outputs/registry/stage19_artifact_manifest.json`。

证据强度分为三档：

- **较强**：三数据集、500-query 检索或 60-query 回答实验，可支持当前项目内部的稳定趋势结论。
- **中等**：单数据集 20-query LLM 实验，或方法假设较强的三数据集实验。
- **探索性**：Microsoft GraphRAG official 的 1-query/5-query 结果和诊断，只能说明现象与工程可行性。

## 3. 分层结果解读

### 3.1 自建模拟攻击

最稳定的现象是：Bridge Injection 很容易把新增证据送入 top-k，而 Entity Swap 是否暴露更依赖数据集和原始文档结构。LogicGuard 在这些攻击上能把暴露降到 0，但这部分攻击由本项目构造，防御也知道新增来源和参考内容，因此只能证明机制按设计工作，不能单独作为论文的最终安全结论。

Natural BridgeV2 和真实 LLM 实验比最初模板更接近回答场景。两个模型都会在 poisoned context 下产生攻击目标或错误回答，guarded 能阻断错误，recovered 能恢复部分 clean 正确回答。不过样本只有 20 个，且攻击者没有根据 LogicGuard 规则自适应优化。

### 3.2 LogicPoison 官方语料

这是当前最完整的主证据。攻击语料不是 LogicGuard 自己生成，且在三个数据集的 500-query 检索实验中，changed doc 都稳定进入 top-k。回答层结果形成了清晰链条：

1. `poisoned` 比 `clean` 的 Utility 更低、错误非拒答更高，说明攻击确实影响最终答案。
2. `guarded` 将错误非拒答压到 0，但 UNKNOWN 达到 1，说明单纯删除污染证据只得到“安全但不可用”。
3. `recovered` 同时恢复 Utility 并保持低错误率，说明可信证据回填是 LogicGuard 的关键组成。
4. non-oracle Recovery 的 Utility 从 oracle 的 0.4750 降到 0.4083，但仍明显优于 poisoned 的 0.1167，说明恢复收益并非完全来自 gold doc ID 泄漏。

这组结果仍有两个强假设：存在可信 clean corpus；每个数据集只抽取 20 个 query 进入昂贵的 LLM + Judge 阶段。

### 3.3 Microsoft GraphRAG official

Official 实验已经证明工程接入可行，但还不是论文主表规模。Stage14 的五Query中只有一个 query 的 correct support 完整进入 context，因此 Recovery 正确率只有 0.20。Stage15-17 进一步证明：扩大 `top_k_entities`、关系数量和 context token 并不能改善召回，问题更早发生在 query-to-entity mapping。

Stage18 将五个 query 拆为独立图后，平均 gold support recall 从 0.20 升到 0.80，说明 mixed graph 中确实存在实体簇偏置。但必须同时写清楚：

- independent graph 不是生产共享图，不能作为最终解决方案。
- poisoned changed-support exposure 仍为 1.00，Stage18 没有执行完整 answer-level 防御。
- 三个 workspace 因 community report 阶段问题采用 `community_prop=0` 的 local-only 降级。
- 因此 Stage18 是召回瓶颈诊断，不是“LogicGuard 抵抗 LogicPoison 成功”的新证据。

## 4. 指标定义

| 指标 | 定义 | 方向 | 解释注意事项 |
| --- | --- | --- | --- |
| `hit@k` | top-k 是否至少命中一篇 gold support | 越高越好 | 不代表多跳证据全部齐全 |
| `gold_recall@k` | top-k 覆盖 gold support 的平均比例 | 越高越好 | 被改写 gold 仍可能被计为命中 |
| `trusted_recall@k` | 排除已知改写证据后的可信 support recall | 越高越好 | 需报告有效 query 数 |
| `exposure@k` | 污染证据进入 top-k/context 的 query 比例 | 越低越好 | 不等于最终回答攻击成功率 |
| `changed_gold_exposure` | 被改写 gold support 进入结果的比例 | 越低越好 | 对原位 LogicPoison 最关键 |
| `support_title_entity_hit_rate` | support 标题进入 official selected entities 的比例 | 越高越好 | 是实体映射诊断，不是答案正确率 |
| `correct` | Judge 判为完整正确 | 越高越好 | 受回答模型本身能力影响 |
| `partial` | Judge 判为相关但不完整 | 视任务而定 | 本项目与 correct 合并为 Utility |
| `Utility` | `(correct + partial) / calls` | 越高越好 | 必须同时查看错误非拒答率 |
| `UNKNOWN率` | 模型因缺证或冲突拒答的比例 | 不是单向越高越好 | 高值可能安全但不可用 |
| `错误非拒答率` | 模型明确输出错误且未拒答的比例 | 越低越好 | 当前近似 answer-level ASR |
| `context_recall_failure` | official context 完全没有 gold support | 越低越好 | 这时 Recovery 没有材料可用 |

## 5. 当前可写入论文的结论

1. 新文档注入和原位内容改写需要不同完整性信号；provenance 与 content integrity 具有互补性。
2. LogicPoison 在三数据集上稳定改变检索证据，并显著提高回答层错误、降低 Utility。
3. 只过滤污染证据能够降低错误，但会造成系统性拒答；Recovery 是维持可用性的必要机制。
4. non-oracle trusted retrieval 仍保留大部分恢复收益，表明 Recovery 不完全依赖 gold doc ID。
5. 在 Microsoft GraphRAG official local query 中，query-to-entity mapping 和 support recall 是 Recovery 的前置瓶颈。

## 6. 当前不能写成定论的内容

- 不能声称 LogicGuard 已经抵抗生产级 Microsoft GraphRAG 上的 LogicPoison。
- 不能把 Stage18 的 recall 提升写成污染暴露降低或回答安全提升。
- 不能把轻量 graph surrogate 结果直接称为 Microsoft GraphRAG 结果。
- 不能用 1-query/5-query official 实验声称统计显著。
- 不能把 clean-reference Recovery 描述成无需可信基础设施的现实防御。
